Why Spring Data saveAll() Still Inserted One Row at a Time

We passed a collection of entities to saveAll() and expected batched inserts. PostgreSQL logged one INSERT per row. Switching from identity IDs to explicit sequences allowed Hibernate to batch the writes.

10 min read · Spring Boot · JPA / Hibernate · PostgreSQL · Performance

What we expected saveAll() to do

We had to import a large CSV into two PostgreSQL tables. Each source record became one parent item and up to 24 item_history children. A file with three million source records could therefore produce about 75 million database rows.

Our first implementation collected entities and passed them to Spring Data's saveAll(). The IDs were backed by PostgreSQL BIGSERIAL columns and mapped as identity values: 

@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;

itemRepository.saveAll(items);

From the Java side, this looked like a batch operation: one collection went into one repository method. We expected Hibernate to send the inserts to PostgreSQL together.

Then we checked the database logs. PostgreSQL was receiving individual statements: 

insert into item (...) values (...);
insert into item (...) values (...);
insert into item (...) values (...);

saveAll() had grouped the work at the repository API, but it had not grouped the SQL sent to the database. With millions of parent and child rows, that distinction dominated the import time and placed unnecessary load on a database shared with other workloads.

What we changed. We replaced identity generation with explicitly allocated sequences, enabled Hibernate JDBC batching, and wrote the import in bounded transactions. That let Hibernate know the IDs before inserting the rows, retain several inserts in its write-behind queue, and release each group of entities after it was committed.

saveAll() is not a promise about SQL

Spring Data's method name describes its input: it accepts several entities. Internally, saveAll() still asks the entity manager to persist or merge each entity. It does not construct a multi-row INSERT, and it does not by itself enable JDBC batching.

Hibernate can turn those persistence operations into a JDBC batch, but only when its configuration and entity mappings allow it to postpone the inserts. Our ID mapping did not.

A collection API and a JDBC batch are different layers. Calling saveAll() once instead of calling save() in our own loop made the code shorter. It did not change the identifier strategy or guarantee fewer database round-trips. The database logs, rather than the repository method name, told us whether batching was working.

The ID had to exist before the insert

Our tables used PostgreSQL BIGSERIAL columns. PostgreSQL implements BIGSERIAL with a sequence-backed column default, but our JPA entities treated those IDs as identity-generated values.

With identity generation, Hibernate does not know an entity's ID until PostgreSQL executes its insert and returns the generated value. The parent ID is also needed to create the foreign keys for its history rows. Hibernate therefore had to execute inserts while processing the entity graph instead of leaving them queued for a later JDBC batch.

This explained why changing the repository call was not enough. The obstacle was not saveAll() itself; it was the requirement to obtain every identity value immediately.

We changed identity IDs to explicit sequences

We changed the entity mappings from GenerationType.IDENTITY to GenerationType.SEQUENCE. An explicit sequence lets Hibernate obtain identifiers before it sends the inserts. That makes it possible to keep several new entities in the persistence context and send their inserts as a JDBC batch.

We also allocated sequence values in blocks. Hibernate fetched a block from PostgreSQL and assigned IDs from that block in memory instead of making a sequence call for every row: 

@Entity
public class Item {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "item_seq")
    @SequenceGenerator(name = "item_seq", sequenceName = "item_id_seq",
                       allocationSize = 120)   // one fetch per parent batch
    private Long id;
}

@Entity
public class ItemHistory {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "item_history_seq")
    @SequenceGenerator(name = "item_history_seq", sequenceName = "item_history_id_seq",
                       allocationSize = 720)   // matches hibernate.jdbc.batch_size
    private Long id;
}

We used an allocation of 120 for parent IDs and 720 for history IDs. These were implementation settings, not magic values: they were chosen around the number of entities we held and wrote at a time. The important change was that ID generation no longer forced an insert for every entity as soon as it was persisted.

The mapping and schema have to agree. We defined the sequences in the database migrations and kept their increments consistent with the corresponding allocationSize. That made the ID allocation strategy explicit in both the Java mapping and the PostgreSQL schema.

We enabled JDBC batching and checked the logs again

Changing the ID strategy removed the main blocker, but it did not turn batching on. We configured Hibernate to group inserts and to order pending statements by entity type: 

spring.jpa.properties.hibernate.jdbc.batch_size=720
spring.jpa.properties.hibernate.order_inserts=true
spring.jpa.properties.hibernate.order_updates=true

Ordering mattered because one application batch contained two entity types. Grouping all parent inserts together and all history inserts together gave Hibernate a better chance of filling each JDBC batch.

We then checked the database logs again. This was the verification step that mattered: the original logs had disproved our assumption about saveAll(), and the new logs confirmed that the inserts were now being sent through JDBC batches.

JDBC batching is not necessarily one multi-row SQL statement. Hibernate can submit several executions of the same prepared statement as a JDBC batch. The PostgreSQL driver may rewrite that batch into multi-row SQL when configured to do so, but that is a separate optimisation. We kept those two mechanisms distinct when reading the logs and measuring the result.

We kept each transaction bounded

Effective JDBC batching solved the repeated database calls, but we still could not attach every entity from the file to one persistence context. We streamed the CSV and accumulated 120 parent records at a time. Because a parent could have 24 history rows, one application batch could contain up to 2,880 child entities as well. 

List<Item> batch = new ArrayList<>(120);

for (NamedCsvRecord row : csv) {
    batch.add(toItemWithHistory(row));

    if (batch.size() == 120) {
        ingestDbService.saveBatch(batch);
        batch.clear();
    }
}

if (!batch.isEmpty()) {
    ingestDbService.saveBatch(batch);
}

A separate service method owned the transaction for one application batch. It saved the entity graphs, flushed their SQL, and cleared the persistence context: 

@Transactional
public void saveBatch(List<Item> items) {
    itemRepository.saveAll(items);
    entityManager.flush();
    entityManager.clear();
}

Ending the transaction at this boundary kept the amount of managed state stable. Once a batch was committed, the importer no longer needed its entities. The next 120 source records started with a fresh persistence context instead of adding to everything already processed.

This also gave failures a clear boundary. A failed transaction rolled back one application batch, not the entire file and not half of a parent-and-history graph.

The three batch sizes were not the same thing

Most of our initial confusion came from using the word batch for several different layers. We ended up tracking them separately:

  1. The application batch was the 120 source records collected before calling the transactional writer. It bounded memory and transaction size.
  2. The Hibernate JDBC batch was the number of repeated prepared-statement executions Hibernate submitted together. We configured this separately.
  3. A multi-row SQL statement is one INSERT with several VALUES tuples. That only appears when application code constructs it or when the JDBC driver rewrites a JDBC batch.

saveAll() referred to none of these sizes. It was simply the repository entry point we used to submit a collection of entities.

How we arrived at 120 and 720

We did not choose those numbers by trial and error. PostgreSQL's extended query protocol allows at most 65,535 bind parameters in one statement. For a multi-row insert, every column in every row consumes one parameter: 

parameters = rows × bound columns per row

The history table determined our upper bound because it had the largest fan-out. One source record could produce 24 history rows, and one history insert bound about 20 columns. If all history rows from one application batch were rewritten into a single multi-row statement, the worst case was: 

120 source records
× 24 history rows per source record
× 20 parameters per history row
= 57,600 bind parameters

The theoretical ceiling was floor(65535 / (24 × 20)), or 136 source records. We chose 120 instead of running at that edge. It kept the worst case below the protocol limit and left room for small changes to the history-row shape.

A full application batch could expand to 2,880 history entities (120 × 24). We split those into JDBC batches of 720, giving us four child batches at maximum fan-out. If the PostgreSQL driver rewrote one of those JDBC batches as a multi-row insert, it contained about 720 × 20 = 14,400 bind parameters—well below the same limit. We used 720 for the history sequence allocation as well, so one allocated block covered one full child JDBC batch.

The parameter limit applies to one SQL statement. A plain JDBC batch can contain repeated executions of a prepared statement without combining all of their parameters into one SQL statement. The 65,535 limit becomes relevant when application code or the PostgreSQL driver rewrites those executions into a multi-row insert. We sized both levels so that enabling that rewrite would not push a statement past the protocol boundary.

How we made the import safe to run again

Committing one application batch at a time meant an interrupted import could leave earlier batches in the database. We used a stable external key and an import-specific value to identify rows that had already been written. 

INSERT INTO item (external_id, import_date, opened_on, status)
VALUES (?, ?, ?, ?)
ON CONFLICT (external_id, import_date) DO NOTHING

PostgreSQL's unique constraint remained the final authority. This mattered more than checking for a row in Java: two workers can both observe that a key is absent, but only the database can make the insert atomic with the uniqueness check.

Parent and history rows were written in the same transaction, so we did not commit a parent with only part of its history. A retry could skip completed records and attempt the failed application batch again.

Where we would take this next

The JPA solution kept the existing entity mappings and business logic, which made it a practical change for us. If this import became substantially larger or more frequent, we would test three further changes rather than assume they were faster:

  1. Load into a staging table with PostgreSQL COPY, then merge into the destination tables with set-based SQL.
  2. Enable the PostgreSQL driver's reWriteBatchedInserts option and compare database calls, elapsed time, and load against the current JDBC batches.
  3. Record parse time, transaction time, rows written, and failures per application batch so the next bottleneck is visible before changing the design again.

Recap

Our mistake was assuming that a collection passed to saveAll() implied batched SQL. The PostgreSQL logs showed that every entity was still inserted separately. We fixed the behaviour in the layers below the repository method:

  1. Database logs revealed that the identity-based inserts were not being batched.
  2. Explicit, pooled sequences let Hibernate assign IDs before executing the inserts.
  3. Hibernate's batch and ordering settings grouped compatible statements at the JDBC layer.
  4. Small transactional application batches kept the persistence context and failure scope bounded.
  5. Database uniqueness constraints made previously committed work safe to encounter on a retry.

The repository call did not change. What changed was whether Hibernate could postpone inserts, how it sent them to JDBC, and how much work we kept in one transaction.

Related lesson: when an abstraction promises convenience rather than a specific execution strategy, inspect the behaviour at the next layer. In this case, the PostgreSQL logs told us more than the repository method name did.
